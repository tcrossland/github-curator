# Step 7: portfolio

The last step of `repo-review` in portfolio mode (`portfolio`, or `overview`, its old name), read only in that mode. The steps and sections it names (Steps 1 to 6, Timing, The recommendation) are in [SKILL.md](SKILL.md).

**Timing**: log as set out under Timing in `SKILL.md`. Review the repos one at a time. Finish each repo's review, through publishing (or saving) its scorecard, before making any call for the next, and don't run two repos' steps side by side or in one command. Each repo's review keeps its own log and shows it on its scorecard, and the next repo's log starts after the last one's `Build` line. Before each repo's review, write one line of plain text naming it and its place among the repos, `Repo 3 of 10: OWNER/NAME`; its steps then print their own lines, as Progress under Timing says. The portfolio run's log has one line per repo, named `OWNER/NAME`, written as its scorecard is published (or saved, with `no-publish`), then `Build`.

A portfolio run is a full review of every repo, so with more than a handful, run `quick` first for the user's own repos, or `triage` when forks are among them, and pass the repos its `next` command names to `portfolio`.

**The cost, before starting.** Once the repos are known, and before the first one's review, count them. When there are more than 10 (a `next` command names 10 at most), say in one message what the run will take, at about five minutes a repo, and on claude.ai in Manual mode one approval a repo to attach it: `12 repos, about an hour; on claude.ai in Manual mode, 12 approvals to attach them`. Offer a quick review of them instead, or a full review of the first 10, and wait for the answer. When no one can answer, as in a scheduled task, run what was asked and give the estimate in the footer.

Use the repos given. If none are given, list the user's repos with `list_repos`, keep the ones the user owns, public and private, forks included, leaving out those already archived, and say in the page's footer which repos were included and how they were chosen.

After each repo's scorecard is published (or saved, with `no-publish`), publish or save one more page from the same template, titled "Portfolio overview", with the icon `checklist`. Republish to an existing "Portfolio overview" artifact if `list_artifacts` finds one. Its JSON:
- `overview`: `true`
- `title`: "Portfolio overview"; `subject`: how many repos and which commits; `date`
- `verdict`: `fix` (the repo that needs attention first, and its most important fix) and `why` (one or two sentences). Pick the repo whose earliest failing question comes first; break ties by the most fails.
- `pins`: `current` (the pinned repos and gists now, as `owner/name` strings), `recommended` (up to six, in the order to pin them, chosen across every repo reviewed and the current pins that weren't), `source` (where the current pins came from, with Step 1's label "profile page summary, may not be complete" when they came from that summary, which can leave pins out) and `why` (one or two sentences on what changes and why). Rank the repos whose feature call is yes, and keep a current pin that wasn't reviewed unless something reviewed is clearly stronger.
- `repos`: one object per repo with `name` (owner/name), `link`, `action` (its recommended action), `feature` (`true` or `false`), `todo` (the number of `todo` items before the action and featuring, or 0), `statuses` (the seven statuses in order), `fix` (that repo's verdict fix), `stars`, `views` (14-day views, or "Not available"), `scorecard` (the scorecard's claude.ai URL, or its file path with `no-publish`), and `fixPrompt`: the repo's own scorecard `fixPrompt`, copied as it is with every item, left out when its scorecard has none. Keep one per repo; don't merge them into one prompt.
- `timings`: the rows from the portfolio run's log, one per repo, then `Build`, as set out under Timing
- `footer`: which repos were included and how they were chosen

Reply in three lines: the repo that needs attention first with its fix; the recommended pins, in order; then one `name: ACTION (featured), N pass · N fail · N flagged` entry per repo, with "(featured)" only when its feature call is yes, separated by semicolons. Take that third line exactly as the counts script in Step 6 prints it from the page's JSON (`python3 counts.py PORTFOLIO.json`), not counted by hand; if it prints `cannot count`, fix that repo's `statuses` and rebuild the page first.
